# advanced/05 — development certificates and TLS

A TLS broker on a laptop, and the reason its certificates cannot reach
production.

## What it shows

- **`devcerts.Generate`**: an authority, a broker certificate, a client
  certificate, their keys, and a `rabbitmq.conf` pointing the broker at them.
- **A connection over `amqps://`** that publishes and consumes, and a second one
  presenting a client certificate.
- **Three refusals**, each asserted: the marker without the flag, the marker
  **under `Insecure()`**, and TLS settings against an `amqp://` URL.

## Running it

This is the one example that needs a broker of its own, because it needs a TLS
listener holding certificates this repository generated:

```bash
go run github.com/AceMQ-Company/acemq-go-amqp/cmd/acemq-certs@v0.5.0 --out certs --broker localhost
chmod 644 certs/server.key
docker compose --profile tls up -d
go run ./advanced/05-development-certificates
```

The `chmod` is worth understanding rather than copying. The generator writes
private keys `0600`, which is right for a key and wrong for a container that runs
as another user. RabbitMQ reports an unreadable key as a listener that failed to
start, which is a long way from what it is.

`certs/` is gitignored, along with `*.crt`, `*.key` and `*.pem`. These are
generated on the machine that runs them and belong nowhere else.

The example generates a set into a throwaway directory purely to show the files;
the ones it connects with are the ones the broker was started on. Regenerating
them under a running broker is a handshake failure that takes a while to work
out, because nothing about the message says the certificate changed.

## `even under Insecure` is the example

`security.Insecure()` encrypts and verifies nothing: it accepts any certificate
from anybody. It still refuses this one.

That is not a courtesy. A generated authority's private key sits next to its
certificate and usually ends up in a repository, so a development certificate
that could reach production would be an authority **anybody who can read that
repository can issue against** — and the connection would succeed. The marker
makes that impossible on every path rather than on the paths somebody remembered.

The way through is `AllowDevelopmentCertificates()`: a named method a reviewer
will see in a diff, and one more thing to `grep` for in a deployed configuration.

Java, .NET, Python and Ruby stamp the same string and enforce it the same way, so
a certificate generated by any of the five generators is refused by all five
libraries.

## Naming an authority replaces the trust store

`TrustCertificateAuthorityFile` does not add to the machine's trust store, it
replaces it. That is the point: a broker holding a certificate from a public
authority is not your broker, and the several hundred authorities a machine
trusts by default are several hundred ways to be wrong.

A self-signed broker certificate works here too — put the broker's own
certificate in the file and it becomes the one authority you trust.

## TLS settings on a plaintext URL

Refused rather than ignored. A service that was handed a certificate authority,
connected in plaintext and reported success is the failure the whole arrangement
exists to prevent. The mirror image is refused too: `security.Disabled()` against
an `amqps://` URL.

## The client certificate

The generated `rabbitmq.conf` sets `verify_peer` with
`fail_if_no_peer_cert = false`, so the broker validates a client certificate if
one is presented and does not insist on one — which suits a development broker
that is also reached by password.

So the second connection here proves the certificate was **accepted**, not that
it was demanded. Proving a broker demands one needs a broker started with
`fail_if_no_peer_cert = true`, and the assertion worth writing against it is that
a connection *without* a client certificate is refused: a broker that never asked
looks exactly like one that asked and was satisfied.

## What is not here

`security.Insecure()` is used in this example only to be refused, and should not
be used anywhere else. It encrypts the traffic and checks nothing at all about
who is on the other end, so somebody who can answer on the address in your URL
receives every message you publish and every password you log in with — over a
connection that looks encrypted in every log and every metric.

`TrustCertificateAuthorityFile` is one line more work.

## Credentials

`WithCredentials` takes them from somewhere that is not the URL:

```go
security.Required().
    TrustCertificateAuthorityFile("certs/ca.crt").
    WithCredentials(security.EnvironmentCredentials("MQ_USER", "MQ_PASSWORD"))
```

Credentials given there override anything in the URL, which is how a password
stays out of logs, process listings and crash reports.
`security.FileCredentials` reads one from a mounted secret;
`security.Credentials.String()` never prints it.
